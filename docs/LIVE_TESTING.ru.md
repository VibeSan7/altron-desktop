# Проверка с настоящей моделью

[English](LIVE_TESTING.md) | Русский

Это дополнительная проверка для разработчика, не инструкция установки для пользователя. Обычные `npm test`, `npm run test:native` и Python-тесты не отправляют контрольную задачу внешней модели.

`npm run test:live` по умолчанию пропускается. Он начинает работу только при `ALTRON_LIVE=1` и явно заданных модели, провайдере, каталоге Hermes и его среде выполнения. Запуск использует существующее подключение владельца и может расходовать его лимит или оплачиваемые токены. Не включайте его в обычный CI и не запускайте без разрешения владельца подключения.

## Границы

- Создаётся новый именованный профиль `altron-qa-<случайный-id>` штатной безопасной распаковкой архива в новое имя. Существующий `altron` не перезаписывается.
- Модель и провайдер задаются только новому QA-профилю штатным `hermes config set`.
- Открывается отдельный тестовый Desktop с отдельными настройками окна и каталогом UI-плагинов. Он подключается к отдельно запущенному `hermes serve --isolated` на `127.0.0.1` через штатный remote-режим. Имя QA-профиля передаётся явно; перед заданием проверяется отсутствие прежних сессий в нём. Текущее окно пользователя не управляется и не закрывается.
- Ключи, токены, пароли, `.env` и `auth.json` пользователя тест не копирует. Для своего временного сервера он создаёт отдельный случайный токен в `.env` нового QA-профиля; значение не публикуется. Работает штатный механизм доступа Hermes. Проверенная версия Hermes допускает чтение общего подключения провайдера из нового профиля, если в нём нет собственного подключения.
- Окружение дочернего процесса ограничено системными переменными. Личные переписки и проекты не используются как входные данные.
- Изменения основного `config.yaml` проверяются побайтово; основной профиль не перенастраивается.
- Тест создаёт искусственный `input.json` со случайным маркером. Только модель должна создать `result.json` и передать его через `altron_update`.
- В обычном режиме проверяется один запуск; при `ALTRON_LIVE_TEAM=1` — два согласованных шага с передачей `result.json` → `handoff.json`, точной контрольной суммой первого файла и выбранными инструкциями специалиста. В обоих режимах проверяются выбранная модель и провайдер, настоящее завершающее событие Hermes, статус «Нужна приёмка», содержимое JSON и SHA-256.
- Кнопка приёмки нажимается тестом только после независимых программных проверок искусственного файла. Это не отдельная проверяющая модель и не приёмка реальной пользовательской задачи.
- После полного закрытия и повторного запуска тестового Desktop **и тестового сервера** проверяется неизменность принятой задачи и количества запусков.
- Нет автоматической повторной отправки. Неудачный прогон сохраняется отдельно. Новый запуск теста — отдельная попытка, требующая выяснения результата предыдущей.

## Запуск разработчиком

Требуются установленный Hermes с собранным Desktop, его Python, Node.js и собранный архив `dist/altron-<версия>.tar.gz`. `ALTRON_JS_HOME` указывает на `apps/desktop`, `ALTRON_PYTHON` — на Python установленного Hermes, `HERMES_HOME` — на основной каталог настроек Hermes, не на вложенный профиль.

В Git Bash задайте **не секреты**, а пути и точные идентификаторы подключения. Подставьте свои значения:

```bash
export ALTRON_JS_HOME='C:/path/to/hermes-agent/apps/desktop'
```

```bash
export ALTRON_PYTHON='C:/path/to/hermes-agent/venv/Scripts/python.exe'
```

```bash
export HERMES_HOME='C:/path/to/hermes-home'
```

```bash
export ALTRON_LIVE_MODEL='your-exact-model-id'
```

```bash
export ALTRON_LIVE_PROVIDER='your-provider-id'
```

После явного разрешения на этот запуск:

```bash
ALTRON_LIVE=1 ALTRON_LIVE_TEAM=1 npm run test:live
```

Один прогон ограничен 15 минутами; ожидание ответа модели — 10 минут. Подключения настраиваются средствами Hermes, не переменными с секретами внутри этого теста. Тест не выполняет вход и не просит код подтверждения.

## Проверка обновления без ИИ

`npm run test:upgrade` требует `ALTRON_JS_HOME`, `ALTRON_PYTHON` и `ALTRON_OLD_ARCHIVE` — полный путь к скачанному архиву ранее выпущенной версии 0.2 или 0.3. Перед запуском сверяйте его SHA-256 с опубликованным выпуском. В `dist/` должны быть собраны основной архив текущей версии и её архив обслуживания. Для каждого старого выпуска выполняется отдельный прогон. Если старая версия поддерживает командные планы, тест дополнительно создаёт незапущенный план, отменяет его через новую панель обслуживания и проверяет сохранность плана/шагов без создания исполнений.

Тест импортирует старый профиль через настоящий Desktop, создаёт проект и задачу, импортирует отдельный профиль обслуживания, обновляет код, перезапускает Desktop, сохраняет новое решение, возвращает старый код через профиль обслуживания и проверяет сохранность обоих поколений данных. Временные `.env` и `auth.json` содержат только искусственные контрольные значения; подключение ИИ не используется. Настоящие API-ответы не подменяются; автоматизируется только выбор файла в системном диалоге. Доказательства сохраняются в `.hermes/upgrade-…`.

## Результаты и сохранение

Путь к `.hermes/live-…` печатается в выводе. Там остаются границы прогона, искусственные входной и выходной файлы, запись задачи, итог проверок и изображение результата при успехе. QA-профиль с историей сохраняется для расследования; автоматического удаления нет. `.hermes/`, `dist/` и `node_modules/` исключены из Git. В GitHub переносится только отдельно проверенный обезличенный отчёт, не весь каталог прогона.

Успех этого теста подтверждает конкретный путь «согласовать → запустить → получить файл → проверить → принять». Он не является проверкой установки самого Hermes на чистой Windows 11, первого входа нового аккаунта, всех провайдеров или всего набора требований пользовательского выпуска.
